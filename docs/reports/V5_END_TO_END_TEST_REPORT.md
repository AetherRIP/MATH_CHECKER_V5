## 4. Verification effectiveness

`backend/app/engine/verify.py` is deterministic Python, not a second AI opinion.
It checks: per-question bounds (`0 ≤ awarded ≤ max`), recomputed totals versus
stored totals, M/A/B code counts versus maximum, blueprint coverage
(missing/extra questions, missing subquestions, conflicting rows, clamped
awards), per-question REVIEW status, and scheme-audit discrepancies. It never
rewrites a mark.

What it did on the real run:

* Consistent, correct result → `VALID`, `verified: true`, 0 anomalies,
  0 warnings, no review questions.
* The scheme-header defect was caught **upstream** in the blueprint record, not
  in the result: `total_mismatch`, severity warning, needs_human, "Question
  marks add up to 7 but the mark scheme states 8 — 1 mark(s) unaccounted for."
  The marker used the summed 7, not the printed 8.

What it catches when fed deliberately inconsistent results (deterministic test
of the real function, no AI, no quota):

| Injected defect | Result |
| --- | --- |
| Awarded 5 on a 4-mark question | `REVIEW`; anomaly "awarded 5 marks but its maximum is 4"; stored-total mismatch also flagged |
| Stored total 4 while questions sum to 6 | `REVIEW`; "recomputed value is authoritative" |
| Scheme declares question 3, marker returned nothing | `REVIEW`; "UNMARKED (not a confirmed 0)" |
| Declared subquestion 1(c) never marked | `REVIEW`; same UNMARKED anomaly at subquestion level |

**What it does not do:** it does not re-solve the mathematics. If the model had
awarded 2/2 on 1c — mathematically wrong but internally consistent with the
scheme's maxima — the verifier would have reported `VALID`. Verification is
consistency and coverage checking, not independent re-marking. The accuracy
guarantee comes from the external reference comparison (this report), not from
`verify_result`.

## 7. Defects and fixes

**D1 — The reference accuracy harness cannot see subquestion marks (tooling, unresolved).**

* Reproduction: run `backend/scripts/verify_marking_reference.py --live --ack REFERENCE --only paper-b`.
* Expected: 4 reference items compared (1a, 1b, 1c, 2).
* Actual: `compared 2/4 items`, `matching_errors: {"unmatched_model": ["1"]}`, exit 1, even though the stored result contains 1a = 1/1, 1b = 1/1, 1c = 1/2 and the total is correct.
* Root cause: `align()` in `verify_marking_reference.py` reads only the top-level `questions[].question_number` of the result. `blueprint.reconcile()` deliberately merges part rows into their parent question, storing the per-part detail in `questions[].subquestions`, which the harness never reads. The harness does recognise the group row (`matched_by: "group"`) but still counts the missing individual rows as a matching error.
* Fix: none applied. Changing the metric changes how accuracy is measured across the whole reference set and needs the owner's decision. The marking output itself is correct.
* Regression: n/a (no code changed).

**D2 — Corrupt PDF accepted at upload (application, unresolved).**

* Reproduction: `POST /api/corrections/unified` with any 2 KB random file named `corrupt.pdf` and a valid scheme.
* Expected: rejection with a readable-file error before a job is created.
* Actual: HTTP 200, `page_count: 0`, job queued; the UI is told the standard workflow will mark it.
* Root cause: `pdf_inspect.page_count()` returns 0 for unreadable files by design, and `unified_correction()` tolerates 0 instead of raising `bad_file` when both the page count and the file signature show an unreadable document.
* Impact: low for marks (the live worker cannot mark it), moderate for the teacher (failure appears later as a provider/processing error).
* Fix: none applied — it changes upload behaviour and needs a product decision about PNG/JPG uploads, where a page count of 0 is less conclusive.

**D3 — Blueprint `NEEDS_REPAIR` is not carried into the result's warnings (observation).**

* The blueprint record stored `verification.state = NEEDS_REPAIR` because of the
  scheme-header anomaly, but the result's `verification_json.warnings` was empty
  and its status `VALID`. The defect was detected and the correct total used; it
  simply is not repeated on the result surface (the scheme-review surface owns
  it). Not classified as a marking defect.

**D4 — Verification can report a total above the available maximum (observation).**

* Injected 5/4 produced `earned: 8, available: 7` in the verification block
  alongside `status: REVIEW`. The verifier deliberately never alters marks, and
  the blueprint layer clamps on reconciliation, so a real pipeline run cannot
  normally store this. Worth noting for any UI that displays the verification
  total without checking the status.

**No application code was changed for this test.** The only new file is this
report; all run artifacts are in the git-ignored `docs/logs/`.

## 8. Coverage limitations

* **One synthetic paper only.** The random draw selected paper B (7 marks, 4
  items, nested subquestions, defective scheme header). Paper A (29 marks, 12
  questions, alternative methods, follow-through, missing and ambiguous answers)
  was not run.
* **No real student work.** Deliberate: real submissions are in `data/` and
  would require redaction to report on. Nothing from `data/` was read or written.
* **Digital text only.** Both PDFs carry selectable text. Handwriting, scanned
  pages, OCR and mathematical-expression recognition were not exercised; the
  repository has no OCR engine of its own (Gemini reads the rendered pages).
* **Manual upload path only.** Google Classroom ingestion, sync and write-back
  were not exercised (Testing-only mode blocks writes by design, and no
  Classroom submission was selected).
* **One model.** Marking ran on `gemini-3.6-flash` because the two preferred
  models were unavailable. Behaviour of the newer models is unverified.
* **No export.** Assignment/class report generation and PDF/XLSX export were not
  exercised end to end.
* **No persistence-failure test.**
* **Reference not human-certified.** `manifest.json` still has
  `review.verified_by = null`; the harness correctly reports NOT CERTIFIED. The
  independent check in this report is a clause-by-clause derivation by the
  tester, not a teacher's sign-off.
* **Verification is not mathematical re-marking** (§4), so a confidently wrong
  but consistent mark would pass it.

## 9. Final assessment

The selected workflow ran end to end against a real model and a real mark
scheme: upload, optimisation, scheme reading, queueing, live marking,
subquestion attribution, deterministic verification, persistence and read-back
all completed. The awarded marks matched the independently derived reference
exactly, item by item and in total (6/7; 1a 1/1, 1b 1/1, 1c 1/2, Q2 3/3), and

under-reports because it ignores `subquestions` (D1), a corrupt PDF is accepted
at upload (D2), the reference set is uncertified, and the provider was having a
real outage that forced the run onto the third-choice model. None of these
produced an incorrect mark in this test.
