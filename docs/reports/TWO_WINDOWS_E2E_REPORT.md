The brief asks for **two separate Windows PCs/VMs**. Only **one Windows host** is
available in this session, so the "two Windows environments" were realised as two
**genuinely independent installations** — separate agent directories, separate
persistent device ids, separate data directories, separate credential stores —
talking over **real HTTP** to an **isolated test backend**:

* test backend: `127.0.0.1:8643`, data dir `data_e2e/` (fresh DB, `MC5_LOGIN_REQUIRED=0`).
  The workspace cleanup later moved that directory to `dev_local/archive/data_e2e/`
  (it is regenerated by the harness; nothing in the app reads it).
* **no production database, no production accounts, no production channel touched**
* Installation A = "Developer PC", Installation B = "Assistant PC"

What this proves: registration, roles, teams, publish → discover → download →
verify → install → report, ON/OFF, duplicate prevention, audit, permissions —
all against the **actual backend and the actual agent/updater code**.

**BLOCKED (prerequisite unavailable — not executed):**
physical second machine; clean-VM install; Windows OS restart; real network
partition/unplug; genuinely independent OS/network stacks. These are listed as
BLOCKED below and are **not** reported as passed.

## 2. Defect found and fixed (the point of the exercise)

**T24 initially FAILED.** A valid, published **Linux-only** release was offered to
a **Windows** installation. Root cause was twofold:

1. `updates.device_context()` reads a `platform` column from `devices` — but the
   `devices` table **had no such column**, so the platform was always `None`.
2. `updates.requests_for_device()` derived only the device's *version* from
   `device_context()` and left `platform=None`, so `release_compatible()`'s
   platform gate was a **no-op** even had the column existed.

**Fix (cause, not symptom):**
* [schema.py](../../backend/app/distributed/schema.py): additive
  `devices.platform`, `devices.arch` columns (existing rows stay NULL = unknown,
  preserving today's behaviour until a device reports).
* [agents.py](../../backend/app/distributed/agents.py): `register_device`
  records platform/arch (`COALESCE` so a partial report never erases them) and
  `normalize_platform()` canonicalises `win32`/`macOS`/etc.
* [updates.py](../../backend/app/distributed/updates.py):
  `requests_for_device()` now derives **both** version and platform from the
  device's last report.
* [tiny_agent.py](../../backend/app/distributed/tiny_agent.py): the agent
  reports `host_platform()`/`host_arch()` on register and heartbeat.
* [routes.py](../../backend/app/distributed/routes.py),
  [discovery.py](../../backend/app/distributed/discovery.py): accept platform/arch.

**Retest:** T24 now PASSES for the correct reason (a real 5.2.0 Linux release is
published and then **not** offered to the Windows installation). A regression test
`test_device_platform_is_recorded_and_filters_releases` was added.

## 6. Bottom line

The system works end-to-end across two independent installations through the
real backend: accounts/roles, teams, the **complete signed update path**, all
requested failure rejections, agent ON/OFF, duplicate prevention and audit. One
real defect (platform filtering) was found and fixed. The remaining acceptance
criteria that depend on a **second physical Windows environment** could not be
executed here and are reported BLOCKED rather than passed.
